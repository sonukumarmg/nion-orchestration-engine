## How to Read a NION ORCHESTRATION MAP

Each output file is divided into four structural sections. Here is the reference guide for interpreting them.

---

### Section 1 — Header Block

```
╔══════════════════════════════════════════════════════════════════════╗
║      NION ORCHESTRATION MAP  ·  aiNions Enterprise AI Platform      ║
╚══════════════════════════════════════════════════════════════════════╝
  Message ID  :  NION-YYYYMMDD-HHMMSS
  Timestamp   :  2024-06-15T14:30:22.451823
```

| Field | Meaning |
|---|---|
| `Message ID` | Unique run identifier. Format: `NION-{date}-{time}`. Used to correlate entries in `nion_orchestration.log`. |
| `Timestamp` | ISO-8601 datetime of when orchestration started. |

---

### Section 2 — L1 PLAN (Orchestrator Layer)

```
📋  L1 PLAN  (Orchestrator Layer)

  Intent        :  Extract action items and escalate CI/CD blocker
  Message Type  :  MEETING_TRANSCRIPT
  Gaps          :  None identified ✓

  Routing Plan:

  [TASK-001]  ──▶  TRACKING_EXECUTION
    │  Rationale  :  Extract structured tasks, risks, and sprint decisions
    │  Priority   :  HIGH
    └  Hints      :  extract tasks with owners and due dates, identify blockers

  Cross-Cutting Requested  :  knowledge_retrieval, evaluation
```

| Field | Meaning |
|---|---|
| `Intent` | One-sentence summary of what the sender needs — generated by the L1 LLM. |
| `Message Type` | Classification: `status_query` · `feasibility` · `decision_request` · `meeting_transcript` · `escalation` · `ambiguous` |
| `Gaps` | Missing context or ambiguities detected by L1. Empty (`[]`) means the message was complete. Non-empty gaps indicate L1 had to make assumptions. |
| `[TASK-XXX] ──▶ DOMAIN` | Each task represents one L2 domain activation. L1 **only** names the domain — never individual L3 agents (visibility enforcement). |
| `Rationale` | Why L1 selected this domain for this task. |
| `Priority` | `HIGH` · `MEDIUM` · `LOW` — determines urgency of domain execution. |
| `Hints` | Plain-English capability descriptions. Advisory only — L2 decides which agents to invoke. |
| `Cross-Cutting Requested` | Which shared services L1 explicitly requested. |

---

### Section 3 — L2/L3 EXECUTION (Coordinator → Agent Layer)

```
⚙️   L2 / L3 EXECUTION  (Coordinator → Agent Layer)

  ┌── [TASK-001]  TRACKING_EXECUTION
  │   Summary  :  TRACKING_EXECUTION | TASK-001 | 2/2 agents succeeded | Priority: HIGH
  │   Agents   :  action_item_extraction, risk_tracking
  │
  ├──▶ [✓] action_item_extraction             (1243ms  SUCCESS)
  │         total_count  :  5
  │         action_items :  [{"id": "AI-001", "owner": "James", ...}]
  │
  ├──▶ [✓] risk_tracking                      (987ms  SUCCESS)
  │         overall_risk_level  :  HIGH
  │
  └────────────────────────────────────────────────────────────────────
```

| Field | Meaning |
|---|---|
| `[TASK-XXX] DOMAIN` | The L2 domain coordinator block. Matches a task from the L1 Plan. |
| `Summary` | Coordinator-level result: domain · task ID · agent success ratio · priority. |
| `Agents` | The L3 agents the coordinator selected and invoked (chosen from its visibility scope only). |
| `[✓] agent_name` | Agent executed successfully. Output keys shown below. |
| `[⚠] agent_name` | Agent returned `PARTIAL` status — LLM call may have timed out or returned malformed JSON. Fallback data used. |
| `(Xms  STATUS)` | Execution time in milliseconds and status code. |
| Output keys | The top 3 keys from the agent's structured JSON response. Full payload available in `--verbose` mode. |

---

### Section 4 — Cross-Cutting Agents (Shared Services)

```
🔗  CROSS-CUTTING AGENTS  (Shared Services)

  [✓]  knowledge_retrieval  (SUCCESS)
        project_name      :  Project Phoenix
        relevant_sprint   :  Sprint 14
        context_retrieved :  ['Sprint 14 in progress', 'API 70% complete', ...]
        relevance_score   :  0.87

  [✓]  evaluation  (SUCCESS)
        tone_ok           :  True
        accuracy_score    :  8
        overall_quality   :  GOOD
```

| Agent | Phase | Purpose |
|---|---|---|
| `knowledge_retrieval` | Phase 1a (pre-planning) | Fetches project context. Output is injected into the L1 prompt, grounding routing decisions in project facts. |
| `evaluation` | Phase 3 (post-execution) | Quality-checks all L2 outputs for tone, accuracy, and completeness. |

**`evaluation` quality levels:**

| `overall_quality` | Meaning |
|---|---|
| `EXCELLENT` | All outputs are accurate, complete, and professionally toned |
| `GOOD` | Outputs meet quality standards with minor room for improvement |
| `ACCEPTABLE` | Outputs are usable but have notable gaps |
| `NEEDS_REVIEW` | Quality issues detected — human review recommended |

## Architecture Validation — What the Outputs Prove

A correctly functioning NION engine demonstrates the following in every output:

1. **L1 visibility rule** — The `L1 PLAN` section names only L2 domains (`TRACKING_EXECUTION`, `COMMUNICATION_COLLABORATION`, `LEARNING_IMPROVEMENT`). No L3 agent names (e.g. `action_item_extraction`, `meeting_summary`) appear under `[TASK-XXX]`.

2. **L2 visibility rule** — Agents listed under `TRACKING_EXECUTION` are only from its assigned set. `COMMUNICATION_COLLABORATION` agents never appear under a `TRACKING_EXECUTION` task block, and vice versa.

3. **Cross-cutting integration** — `knowledge_retrieval` always runs in Phase 1a (before the L1 plan is shown), confirming context was injected into routing. `evaluation` always appears in the final section.

4. **Graceful degradation** — Any agent showing `[⚠] PARTIAL` still has output data (fallback payload), and sibling agents in the same domain continue to execute normally.
